# 搜索与语法（调研归并）

调研时间：2026 年 10 月 1 日至 22 日。由同主题旧报告归并；原文与完整来源清单见 Git 提交 `3c14cd8` 的 `docs/reports/`。

## 语法高亮

### 结论（2026-10-01）

继续用 GPUI Kit 的 Tree-sitter 链路，按需启用 Kit 已有语言 feature，完善文件映射；不换引擎。

当时的问题是配置而非能力：`language_for` 只有 Rust、Markdown、Diff 映射到 grammar，JSON 等返回 `plain`，而 JSON grammar 已在依赖里。JSON／JSONC 映射当轮已修。

### 方案比较

| 方案 | 语言与主题 | 成本 | 判断 |
| --- | --- | --- | --- |
| Kit Tree-sitter | 语言由 grammar + query 决定；注入 query 处理嵌入语言；主题按 capture 映射 | 每个 grammar 增加编译代码／query；打开文档还有树与缓存 | 首选 |
| Syntect 5.3.0 | Sublime `.sublime-syntax` + `.tmTheme`；默认 Oniguruma，可换纯 Rust `fancy-regex` | 需实现 highlighter 适配、范围缓存、取消与 scope 映射 | 备选，先以一个弱项证明收益 |
| vscode-textmate / Shiki | TextMate 生态，接近 VS Code | 需要 JS 执行或跨进程；README 自述 cross-grammar injection 有限制 | 将来 HTML 预览或 Web 输出再考虑 |

Tree-sitter 只给语法树与 query 高亮；跨文件推断、符号解析、LSP semantic tokens 是另一层。增加高亮语言不等于引入 LSP。

### JSONC 的准确边界

本地 `tree-sitter-json` 0.24.8 支持 `//`、`/* */` 注释（作为 `extras`），Kit 的 query 有 `(comment) @comment`，别名含 `jsonc`；但 grammar 没有尾逗号产生式。错误恢复后继续高亮不等于 JSONC 校验通过。旧文建议状态栏区分「JSON」与「JSON with Comments」，并测带注释／尾逗号 fixture。

### 落地建议（历史）

顺序：先修已有覆盖 → TOML／YAML／Python／Bash → JS／TS／TSX／HTML／CSS → Go／C／C++／Java／SQL 按工作集。每组测 `cargo tree` 去重行数、dist 字节与 footprint；二进制 +200 KB 或 footprint +5 MB 需决策记录。验收看未完成语法、长字符串／注释、中文／emoji 边界、连续编辑与撤销后的过期结果、后台取消、主题切换和大文件输入延迟。

### 现状

Kit 语法分批全部启用（ADR 0001），当前 feature 列表含 Rust、Diff、Markdown、Python、TOML、YAML、Bash、JS、TS、TSX、Go、HTML、CSS、C、C++、Java、SQL、Ruby、PHP、Zig、Make、C#、Swift、Kotlin、Lua、CMake、Proto。C#／Swift／CMake／Proto 在 `languages::register()` 用 crate 自带查询重新注册（proto 查询复制到 `crates/app/queries/`）；Kotlin／Lua 用 Kit 自带查询。GraphQL 仍不支持（语法 crate 不带查询，Kit 也是空查询）。批次 5／6 的边际体积与预算调整见 ADR 0001，本文不复述。

语法来源：[Tree-sitter](https://github.com/tree-sitter/tree-sitter)、[Syntect 5.3.0](https://github.com/trishume/syntect/tree/v5.3.0)、[vscode-textmate](https://github.com/microsoft/vscode-textmate)、[Shiki](https://github.com/shikijs/shiki)。

## 代码检索：zvec-grep 与替代（2026-10-09）

### 结论

Rust 实现有望减少 Node 与协议层启动开销，但不能保证整个检索服务内存大幅下降；模型运行时、原生向量索引、项目缓存与并发任务仍占内存。zvec-grep 已通过原生 `zvec_node_binding.node` 使用向量库。

本机导入探针（两轮，显式 GC 后取 physical footprint）：空 Node 14.5–14.6 MB；仅导入 `mcp/stdio-bridge.js` 60.7–61.3 MB；CLI commands + bridge 71.6–72.6 MB。真实 STDIO 两会话各约 105 MB。导入探针不是等价负载，差额不能当泄漏。当时 npm latest 与本机均为 0.2.2；维护者表示当前 TS 实现不计划大改懒加载，后续 Rust 会把向量库移进 Rust 实现（issue #72 回复），这是路线不是实测。

### 替代方案

| 方案 | 定位 | 取舍 | 判断 |
| --- | --- | --- | --- |
| ripgrep + ast-grep CLI | 精确／正则／结构检索 | 按需执行，无常驻模型；无自然语言语义召回 | 常驻内存优先时首选 |
| CocoIndex Code | AST 语义检索，共享 Unix socket daemon | Python 前端 + Rust 内核；full 版 PyTorch；本次源码未见官方 HTTP MCP | 语义检索替换的首选试点 |
| QMD | 本地文档＋代码混合检索，共享 HTTP MCP | 默认模型文件约 300 MB / 640 MB / 1.1 GB（磁盘，不是 RSS）；HTTP 空闲 5 分钟只释放 contexts | 文档库优先，减内存目标下不优先 |
| mgrep | 云端语义检索 | 文件上传 Mixedbread；快照里 MCP `ListTools` 为空 | 仅在接受上传时 |

单换 Qdrant／LanceDB 等向量库不能替代切块、embedding、索引维护、排序与 Agent 接入。

### 建议（属 Agent／工具配置层，不是 ZJ 功能）

1. 优先评估 zvec-grep 的直接 HTTP 连接（已实测省掉转发层）。
2. 已知符号用 rg，结构匹配用 ast-grep；自然语言发现继续用共享 zvec-grep。
3. 需要完整替换语义检索时试 CocoIndex Code，同库测召回、增量正确性、冷热请求、单／多 Agent 与空闲 footprint。
4. Rust 正式发布后做同负载对照，避免重复计算 HTTP 已去除的转发开销。

现状：ZJ 不直接适配这些工具，不管理其模型、索引或守护进程；`mcp_servers` 在新建 ACP 会话时为空。

来源：<https://github.com/zvec-ai/zvec-grep/issues/72>、<https://registry.npmjs.org/@zvec%2fzvec-grep>、<https://github.com/cocoindex-io/cocoindex-code>、<https://github.com/tobi/qmd>、<https://github.com/mixedbread-ai/mgrep>、<https://ast-grep.github.io/>。

## 文件搜索：fsearch（2026-10-11）

结论：ZJ 未使用，也不建议整体替换。fsearch 是 Rust 的 macOS 搜索引擎（0.1.0，MIT，上游快照 `b88f4e9`，2026-10-10），与 Linux 图形应用 FSearch 无关；仓库 2026-10-08 创建，当时无 release，也没有常规 `tests/` 或 CI。

作者基准（M4 Max、830 万文件，未复测）：文件名查询 0.13 ms、内容查询 2.3 ms、CLI 启动到答案 3.3 ms、首次完全可搜索 49 s、首次构建峰值 0.9 GB、Chromium 内容索引磁盘 0.76 GB；daemon 的「63 MB」是全盘索引 under 900 万文件名时的 footprint，不是「ZJ 增加这项功能只需 63 MB」。

ZJ 本机微基准（M5 Pro，直接复用 `PathIndex::search` + `fuzzy.rs`）：596 个 Git 跟踪路径中位 52.79 µs / p95 70.71 µs；20,000 合成路径 584.33 µs，路径索引堆约 0.72 MB；200,000 路径 5.084 ms，堆约 7.21 MB。不能用这张表与作者数据算倍数。

适配差异（决定不能只换依赖）：fsearch 不读项目 `.gitignore`，用硬编码目录与扩展名过滤（会跳过 `vendor`／`build`）；文件大小限 1 MiB（ZJ 全文搜索为 2 MiB）；拼写容错只对 ≥5 字节 ASCII token、首字节须匹配；Unicode 只做 ASCII 小写折叠；`FileMatches` 只有路径与行号／文本，没有匹配 byte span 或文件 stamp，无法直接支撑高亮、捕获组替换和变更校验；索引不覆盖未保存缓冲区。

接入两种形态：进程内 Engine 首次构建固定扫 `/`、没有公开 shutdown；JSON-lines socket 需用户另装并处理权限与版本。daemon 的 `keep_warm(250 ms)` 用 `spin_loop` 保主频，是延迟／能耗交换。上游 issue #16 报告的 FSEvents 记录增长是开放线索，不是已复现泄漏。

有价值的后续范围：百万级路径或跨工作区全盘找文件；借鉴位图预过滤与按目录组织候选；把拼写容错作为独立小改动。若试点，先验证项目根与忽略规则、中文／正则召回、频繁增删、完整匹配与替换数据。

fsearch 来源：[固定源码](https://github.com/noahdunnagan/fsearch/tree/b88f4e9a90703eb7338085b325c2852fcaf131a9)、[FSEvents 问题线索](https://github.com/noahdunnagan/fsearch/issues/16)。
