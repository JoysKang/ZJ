### 2026-11-13 Git 写操作的结果只有一个出口，不可撤销的确认默认取消

- 用户要求先做一次交互审阅，按顺序修复。审阅结论三处：不可撤销的删除 / 丢弃排在 Return 上（原生提示框第一个按钮在最右，也是 Return 的默认）；同一个写入结果同时出现在原生 Critical 弹窗和面板底部的固定结果区，成功提示也长期占位；仓库错误只有「N 项仓库错误」计数，原文藏在 tooltip 里。
- 提示框：`workbench.rs` 新增 `prompt_buttons`（把「取消」标成 `PromptButton::cancel`，Escape 才能答它）与 `destructive_prompt`（取消在前，返回要执行的那一项）。`scm_actions.rs` 的 `irreversible` 只把磁盘上无法还原的写入（放弃、应用外部补丁、工作区级反向应用补丁、中止操作、移除 worktree）改成取消在前；暂存、提交、推送、删除本地 / 远程标签这类可恢复或不改磁盘的操作仍把动作放在 Return。只把「取消」放回第一位的写法不够：上游 `initial_focus_ix` 取最后一个非取消且序号大于 0 的按钮，会把焦点放在动作上，Space 反而直接执行。
- 因此 `vendor/gpui-pre-macos/src/window.rs` 的 `prompt` 加一条 ZJ patch：第一个按钮是 cancel 时不做焦点覆盖，Space 落在取消上。取消按钮本身带 Escape 等价键，它在第一位时就占掉了原本的 Return 等价键，所以 Return 也不会执行动作；执行需要 Tab 到动作按钮或点击（原生 NSAlert 一个按钮只有一个等价键，这点没有绕开）。其他提示的第一个按钮不是取消，行为不变，保存冲突对话框仍停在「保存」。保存、覆盖、重新加载的对话框把两个会丢修改的选项都移出 Return：按钮改成 取消 / 覆盖 / 重新加载（丢弃我的修改）/ 比较。
- 结果只有一个出口：失败打开一个 `AlertDialog`，标题带仓库名与动作，说明「操作可能部分完成；刷新状态后检查仓库」，原文限高滚动、可选中可复制，底部是 复制 / 刷新状态 / 关闭；成功、无变化与提示只写状态栏一行（`note_git_result`），状态栏文字加 tooltip 显示全文，较长的 LFS 指针说明走这里。面板底部的固定结果区（`render_git_feedback`、`SCM_RESULTS_MAX`、每组的 `write_message`）删除。失败的原文在仓库行消失后仍留在弹窗里，所以失败不依赖组是否还在。
- 「N 项仓库错误」在状态栏和 SCM 面板状态行都可点，打开同一个弹窗列出全部原文；Escape、Enter 都能关。两处都用真按钮（状态栏沿用 `status_action`，面板状态行用 `base::Button`），Tab 能到、Return / Space 能开。新增 `theme::DIALOG_WIDTH`、`theme::DIALOG_DETAIL_MAX` 与 `colors.scrim`，没有在界面代码里新写尺寸或色值。

### 2026-11-13 放弃被忽略的未跟踪文件真的删掉，Git 结果移到面板底部

- 用户放弃 `kt_stu_api` 的两个 `docs/sql/*.sql` 后看到「没能删除：…（嵌套的 Git 仓库等不会被删除，请在终端处理）」，但文件从 Changes 列表消失，看起来像已经删除；同时觉得这条提示夹在提交框里不协调。
- 原因：这两个路径被 `.gitignore:3:*.sql` 匹配，却以 `git add -N -f` 的 intent-to-add 形式出现在更改列表（索引列 `.`、工作区列 `A`）。放弃时先 `git rm --cached`，再 `git clean -f`；`clean` 不带 `-x` 时对忽略路径直接跳过并返回 0，文件留在磁盘上，事后检查只能按「嵌套仓库等」猜测原因。索引项被删掉后它们变成普通忽略文件，不再出现在 `git status`，于是看起来删除成功了。
- `git_service/src/write.rs` 两处丢弃用的 `git clean` 加上 `-x`：路径都是用户在当前 Changes 列表里明确选中的，忽略规则恰好在列表生成后开始匹配时也应真正删除。嵌套仓库仍不会被删除（`clean` 没有 `-d`/`-ff`），事后检查与提示保留。临时夹具复现：去掉 `-x` 时新测试失败并给出同一句「没能删除」；加上后文件删除、`git status` 清空。
- 回归：`discarding_an_intent_to_add_file_that_the_ignore_rules_match_deletes_it` 用两个仓库分别覆盖「全是未跟踪」（一次 `git clean`）和「同时有已跟踪修改」（先 `restore` 再 `clean`）两条分支，之后文件不存在、已跟踪文件还原、`git status` 清空。
- 写操作结果不再渲染在提交信息框下：`render_git_feedback` 从 `scm_commit_row` 移到 `render_scm` 末尾，作为列表下方一条带顶部分隔线的固定结果区（详情 / 复制 / 关闭 / 失败时的「刷新状态」保持不变，详情仍限高滚动）。面板级结果不依附具体仓库，摘要前加仓库名；错误仍按原逻辑自动展开，失败写入的对话框不变。结果区最高 `theme::SCM_RESULTS_MAX`（两个展开的结果）并可滚动，多个仓库同时失败时不会把列表挤没。关闭结果仍要 `rebuild_rows()`：无变更仓库仅因保留结果而列出，结果清掉后要重建行才会隐藏。
- 回归：`git_feedback_is_compact_until_details_are_requested` 增加几何断言——结果行在侧栏下半部并贴住底部（而不是出现在顶部提交区）。`cargo test -p workspace-editor --locked` 为 **496 passed、0 failed、3 ignored**。未提交、未打包；原生视觉未复测。

### 2026-11-11 冲突的位置可见与直接跳转
